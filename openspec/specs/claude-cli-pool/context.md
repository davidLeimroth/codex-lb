# Claude CLI subscription pool

This fork adds an optional worker registered through codex-lb's existing model-source API. The worker uses Claude Code 2.1.283 subprocesses, OpenAI Chat Completions and Responses, and request-scoped MCP tools. The Anthropic Messages adapter calls the existing codex-lb chat handler, retaining API-key model enforcement and source usage settlement. Existing OpenAI account routes keep their implementation. The source stream parser additionally records in-band Chat/Responses failures, settles reported partial usage once, and logs failures accurately.

Each account is an independent writable directory under `CLAUDE_BRIDGE_ACCOUNTS_DIR`. One concurrent subprocess per account prevents credential refresh races, and that includes readiness: `/health` skips an account that is running a generation (reusing its last result), and a generation that acquires an account while its `claude auth status` check is running waits for the check to finish. The pool uses round robin selection, cooldown on authentication/rate failures and failover only before any response output. Capacity is exactly one request per account with no queue: beyond N concurrent requests the worker returns 429 with `Retry-After: 1`, and codex-lb's source path does not retry it. A singleton cluster worker hosts the account pool. Do not deploy replicas sharing the same subscription configuration directories.

A `.oauth-token` file in an account directory contains the official `claude setup-token` inference grant (valid for one year). It becomes `CLAUDE_CODE_OAUTH_TOKEN` only for that account's child process. A token that is not an `sk-ant-oat01-` subscription grant makes that account fail readiness and fail over at generation time; the token is never echoed. A distinct grant avoids sharing the workstation's rotating refresh credentials. Alternatively, use the CLI's ordinary `.credentials.json` with its config directory. There is no API-key or paid-provider fallback. Readiness runs `claude auth status`; real authentication failures still surface through generation because status alone is a local credential check.

Subscription-only billing: the worker aborts when the CLI reports API-key auth (`apiKeySource`), a rejected rate limit, or paid extra usage (`rate_limit_info.isUsingOverage` or `rateLimitType: overage`). An overage refusal cools the account down like a rate limit. The CLI only reports overage once a request is already running on it, so a few paid tokens can be spent before the process is killed; keep extra usage disabled on every subscription.

History is serialized as tagged turns in a fresh CLI prompt. Every tag carries a random per-request suffix (for example `<tool_result-3f9a1c0b7d2e id="call_1">`) and attribute values are HTML-escaped, so untrusted turn content such as tool output cannot close its own turn and forge a developer turn. Turn text itself stays verbatim. Tool calls and outputs are preserved as text with call IDs, not replayed as native API history. The CLI's own default agent tools are disabled. Caller functions are advertised through a private MCP process that never returns a tool result or executes code. The worker captures the native model tool message and terminates the process group; the caller executes tools and sends results in its next full-history request.

Supported models: `claude-opus-5-5`, `claude-sonnet-5-5`, `claude-haiku-4-5`, with aliases `opus`, `sonnet`, `haiku` on the standalone worker. The cluster registers the canonical IDs. This is a compatibility subset: text, full-history conversations, function tools, bounded output, effort, and SSE. Images, thinking-block replay, provider-hosted tools, response storage, previous_response_id, background mode and non-default sampling parameters are explicitly rejected. Clients must use HTTP Responses/SSE; native Codex WebSockets and compact endpoints are not a Claude worker contract.

Errors and usage:
- Errors before any output are real HTTP errors, which lets the pool fail over. A CLI "prompt is too long" becomes 400 `context_length_exceeded` (type `invalid_request_error`) and other API `invalid_request_error`s become 400; neither cools the account down.
- After output has started, errors are in-band: a usage chunk then an `error` frame (Chat), or `response.failed` carrying `usage` (Responses). codex-lb's stream usage parser settles that partial usage. The fork's small model-source patch recognizes in-band failures and records their error code while preserving reported usage. It covers the Chat `{"error": ...}` frame, the Responses `error` event, `response.failed`, and a `response.incomplete` carrying an `error` object. A plain `response.incomplete` truncation stays a success. The frames still reach the client, including after a limited key's buffered settlement. A failure with no reported usage releases the reservation, and the limited key gets a 502 carrying the upstream error. A transport failure after a usage frame settles that usage once, while client disconnects still release. Errors raised before output (for example a required tool that was not called) release the reservation, so the tokens that attempt used are not counted.
- Truncated Responses end with `response.incomplete` and an `incomplete` message item.
- Chat usage adds a `prompt_tokens_details.cache_write_tokens` extension (`prompt_tokens` includes it), so the Messages adapter reports `cache_creation_input_tokens` separately from `input_tokens`.

Streaming latency: a stream's HTTP status is committed only at the first output, so failover and pre-output errors stay real HTTP errors. Until then no bytes, not even headers, reach codex-lb or the client. With thinking or a required tool (text is buffered until the tool call is verified) that can take minutes. The worker polls for client disconnects during that wait and reaps the CLI. Operators must keep the model source timeout and every ingress idle timeout above the worker timeout (600 s by default).

codex-lb's own source handlers have the same blind spot: Starlette cancels a handler on disconnect only once a streaming body is being sent, but the source path eagerly awaits the upstream response headers (streaming), the whole body (non-streaming), or the whole stream (limited keys, buffered for accounting) before returning. A real test against a held no-inference upstream showed two disconnected Chat clients still holding two upstream requests seven seconds later. The fork's source patch runs only that upstream HTTP work, plus a disconnect watch that awaits `receive` for `http.disconnect`, in child tasks. On disconnect it cancels and awaits the work, which closes the upstream response and returns its connection, then releases the unsettled reservation, logs `cancelled`/`client_disconnected`, and returns an undelivered 499. Quota enforcement, settlement and request-log writes stay on the handler task with their own sessions; work that already completed is settled normally, except that a stream whose setup finished alongside an observed disconnect is closed rather than started for the departed client (it has no usage yet), and nothing releases a reservation after settlement. The watch deliberately avoids `Request.is_disconnected()`: its pre-cancelled probe can swallow the disconnect inside `BaseHTTPMiddleware`'s receive wrapper, which this app installs. (The worker's own `_until_disconnect` still uses that probe.) Responses source requests also gained the caller-cancellation release and deferred settlement that Chat already had.

Anthropic Messages streaming: text streams live as block 0. Tool calls are collected and emitted after the text block closes, each as one complete `tool_use` block, so no block starts before the previous one stops even when a source interleaves parallel tool deltas. `content_filter` maps to `refusal`; `cache_control` on tools is accepted and ignored; `tool_choice.disable_parallel_tool_use` maps to `parallel_tool_calls: false`. Malformed upstream bodies become Anthropic error envelopes (502 or an in-stream `error` event), not 500s.

The customization is additive over upstream v1.24.0. `Dockerfile.claude` pins the cluster's existing image digest so its PR457/469 native-thread fixes remain intact. Updating the fork source alone does not update that runtime base: validate and update both the upstream source pin and image digest together. The `runtime` stage runs `python -m app.modules.claude_messages.compat`, which imports the entrypoint and checks the `v1_chat_completions` and key-validation signatures, the source-routing hook, the Messages and chat routes, and that the base's `ChatCompletionsRequest` accepts a translated Messages request. A drifted base therefore fails the build, not the primary proxy's startup. That check does not replace running `tests/integration/test_claude_messages.py` against the pinned base's source before rollout. The worker stage verifies the CLI binary against per-architecture sha256 build arguments copied from the official release manifest, rather than trusting a manifest fetched from the same origin at build time. Deployment images are immutable by digest in Talos GitOps.

The source stream fix is tracked as a normal two-file diff against upstream and generated into `patches/claude-source-stream-errors.patch` for the preserved runtime. `scripts/apply-claude-runtime-patch.py` requires each complete context to match exactly once, so different native-thread line numbers are allowed while source drift fails the build. Regenerate the patch from the pinned base when upgrading; never replace the production proxy module wholesale.

Ruff and ty checks passed. The native signed-owner and durable-owner runtime suites passed 4 and 5 tests. Both image targets build, and Linux Claude auth status recognizes the distinct setup-token grant. New OpenSpec capability/change pass strict validation; the full inherited spec collection has 22 pre-existing validation failures (mostly placeholder Purpose sections) that are outside this feature. Real cluster inference and final model availability checks remain pending the explicit account-wide extra-usage decision.

Final Opus 5.5 CLI review found no code blockers. Deployment must pin both worker containers by immutable digest and keep inference disabled until paid usage is disabled. The initial development tags in the prepared manifests are replaced by release digests before promotion. Anthropic error translation preserves Retry-After for capacity/rate errors.


Codex client compatibility (2026-09-30): reviewed [Z.ai Codex setup](https://docs.z.ai/devpack/tool/codex), [DeepSeek Codex integration](https://api-docs.deepseek.com/quick_start/agent_integrations/codex), and [DeepSeek Responses compatibility](https://api-docs.deepseek.com/guides/responses_api). Both providers use Responses plus an explicit model catalogue; DeepSeek also documents stateless full-history requests. The older [erubescent/codex-zai-proxy](https://github.com/erubescent/codex-zai-proxy) illustrates request/tool/SSE translation, while [guajun/codex-deepseek-responses-fix](https://github.com/guajun/codex-deepseek-responses-fix) documents orphan tool outputs and encrypted subagent inputs in newer Codex clients. Their examples are evidence, not installers to execute or configuration files to copy over existing settings.

The bridge accepts and ignores only the explicit non-generative Codex `client_metadata` field on Responses requests; strict unknown-field validation remains. A real native Codex 0.155.0-alpha.9.2 request otherwise failed before inference. After ignoring that field, the bundled runtime completed text inference and a native command/tool-result loop that read, copied, and byte-compared a random proof file. Use the existing `codex-lb` provider ID and backend Responses endpoint so sidebar/task identity stays stable. Disable WebSockets for this provider; Claude requires HTTP/SSE and full input history. The existing model catalogue already advertises Opus 5.5, Sonnet 5.5 and Haiku 4.5. Do not alias Haiku 5.5 to 4.5 or claim unsupported images, native search, compaction, custom tool types, or encrypted subagent history work.
